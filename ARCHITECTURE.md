# Architecture

This document explains the reasoning behind this library's design decisions. For API usage, see `README.md`.

## Why nested sticky instead of pin

GSAP `pin` depends on `pinnedContainer` offsets and accumulated `pin-spacing`, which can drift on resize refreshes when multiple pins share one container.

Pinning each scene directly with `position:sticky` avoids that drift, but only the scene itself freezes, so neighboring content scrolls away and leaves gaps.

This library solves both issues by wrapping the shared container in nested sticky layers and pinning a different layer per scene. The same container can then freeze at multiple scene positions in sequence, with neighboring content frozen together and no visual gaps.

## Nested structure of the Scene and Cover layers

### Scene layer (`createStickyTrigger`)

The shared container gets wrapped in as many nested `stickyContainer > { stickyWrapper(sticky), stickyPadding }` layers as there are triggers. Scenes earlier in DOM order end up nested more deeply, but depth doesn't decide when they freeze. Sticky offsets add up down the nesting, so a wrapper would engage late by the dwell of every enclosing wrapper that has already frozen, and its sticky top makes up for that. Each scene freezes when its trigger reaches its `start` anchor, after every freeze that began first.

```
container2                         ← layer for the 2nd scene
├ wrapper2 (position:sticky)
│  └ container1                    ← layer for the 1st scene
│     ├ wrapper1 (position:sticky)
│     │  ├ .container__inner       ← shared container (the original DOM)
│     │  └ sentinel (flow-root)    ← empty, keeps a trailing margin inside wrapper1
│     └ padding1                   ← spacer equal to the 1st scene's dwell distance
└ padding2                         ← spacer equal to the 2nd scene's dwell distance
```

`padding` defines the dwell distance, and the sticky `wrapper` keeps the container pinned for that duration. GSAP does not pin here; it only advances effects using `start`/`end` values aligned to this freeze window.

A bottom margin ending the shared container, its own or its content's, would collapse out of `wrapper1` and move where its freeze ends; the sentinel holds it in. A flow-root `wrapper1` would also hold in a top margin and shift the container down. Outer wrappers end in a padding div, so they need no sentinel.

### Cover layer (`createOverlapScroll`)

Unlike Scene layers, this does not freeze the whole shared container. Inside `trigger`'s parent, only "everything from the start through `trigger`" is moved into a sticky wrapper; `cover` and later siblings stay outside.

```
.container__inner
├ wrapperB (position:sticky)       ← 2nd cover layer
│  ├ wrapperA (position:sticky)    ← 1st cover layer (absorbed into the nesting as-is)
│  │  └ start … trigger1
│  ├ cover1 …
│  └ … trigger2
├ cover2                           ← brought forward via z-index:1
└ …
```

Making only `trigger` sticky would leave a gap as earlier content scrolls away, so this wraps the whole leading range through `trigger`. The rise effect comes from `cover`'s natural scroll, so no GSAP tween or dwell spacer is needed and document height stays constant.

## Two-pass position measurement

`refresh()` (in `README.md`) runs in two passes: first it measures all natural positions with sticky temporarily disabled, then it applies sticky and padding in DOM order. The split is a correctness requirement, not a performance nicety. A pinned ancestor shifts `documentTop` for its descendants by however far the page has scrolled past its natural engagement point (verified in `e2e/StickyScrollTrigger.spec.ts`'s "documentTop is corrupted by an actively-stuck sticky ancestor"). Carrying the `position:sticky` CSS is not enough on its own. The browser has to have engaged it. `refresh()` can run at any scroll position, including one where an earlier layer is already stuck (a resize-triggered refresh mid-scroll, say), so without the split that layer's offset leaks into every later measurement.

Measurements use `documentTop` (`offsetParent` chain), not `getBoundingClientRect`, so values stay stable across scroll position and across `position:sticky` merely being applied without being stuck. They aren't stable across an element or its ancestor actually being stuck, though, which is exactly why pass 1 resets sticky first, on `createStickyPin`'s pins as well as on the Scene/Cover wrappers.

Another instance's wrappers and pins, and the page's own sticky elements, shift a read the same way once stuck, but the pins and the page's elements are the author's, and a measurement writes nothing to them. It reads at scroll 0 instead, where GSAP measures: GSAP's refresh records the scroll, dispatches `refreshInit`, scrolls to 0, measures every trigger and goes back to its record in one task (ScrollTrigger.js:421, 495, 504, 546), so at 0 each of them sits where GSAP sees it, one stuck there already included, and nothing is painted in between. Inside GSAP's refresh, which scrolls to 0 only once its whole `refreshInit` dispatch is over, the layer handler scrolls there for its own `refresh()` and the other instances' measurements after it, and back to GSAP's record, which gives the way there with no layout read, so the listeners after it see the scroll GSAP shows them. A read anywhere else in GSAP's refresh, from an `onRefresh` say, makes the trip itself. A kill's catch-up in a layer handler runs before that, at the scroll it keeps, with only the other instances' wrappers reset, except for its read of its container's top, which goes to 0 as the measurement it is compared with did; one from the batch's own listener reads as anywhere else in GSAP's refresh. A `refresh()` called directly scrolls there and back itself, as GSAP's own `ScrollTrigger.refresh()` does. Mid-scroll it does so only when something besides the instance's own wrappers and pins can be stuck around what it reads (the same check the reads below make), since the trip would stop the scroll; otherwise its own resets leave nothing stuck, and it measures where the page is, with the same result. A `resolveScrollPosition` or `getScrollTop` call does at rest, when a sticky element besides the instance's own holds what it measures; while the page scrolls it doesn't, since that would stop the scroll, and resets only the other instances' wrappers, the library's own elements, measuring the rest as it sits. Whether the page scrolls is GSAP's `isScrolling()`, so a read waits as long after a scroll as GSAP's own refresh does (200 ms after it, checked every 250 ms, and while a pointer is down; ScrollTrigger.js:193, 335, 1401). A trigger callback GSAP runs on the first scroll after a pause comes before GSAP marks the scroll (ScrollTrigger.js:199-202), so GSAP's update counts as a scroll too, as it does for a kill, except the one that ends GSAP's refresh. GSAP counts the library's own trip too, so while the page is still where a trip begun at rest came back to, within that time, the library counts it as at rest; one begun mid-scroll came back to a page still scrolling. A GSAP refresh a start or end function starts meanwhile takes the real scroll as its record, as it would have at the top level (GSAP keeps one record per scroller, which the outer refresh goes back to as well), and the measurement goes back to 0 once the function returns, or as soon as the function reads or calls `refresh()`, keeping its own way back. Nested-sticky dormancy moves what it left past its freeze to where it sits at 0 for the measurement, without making anything sticky, and back afterwards.

Viewport height is measured via a temporary `height:100vh` element (`measureViewportHeight`) instead of `window.innerHeight`, which fluctuates on mobile address-bar show/hide. This matches GSAP's own approach (`_refresh100vh`).

### Why a Scene layer's end function runs twice

Pass 1 reads the layout with every padding where the last refresh left it. GSAP calls a pin's `end` function in another one: the spacers of the pins refreshed before it in place, those after it reverted. An `end` that reads the page's height in pass 1 counts its own padding, so it grows on every refresh. `#reevaluateLiveEnds` calls each Scene layer's function-valued dwell or absolute `end` again with that layout set up: the instance's own paddings and those of every armed instance later in the page at 0, and after each earlier layer's trigger a spacer as tall as that layer's planned padding. Page order stands in for GSAP's creation order. A clause `end` isn't called again, since pass 2 places its `endTrigger`, and neither is `start`, which GSAP calls once.

The windows are planned in memory until no value moves (six rounds at most) and written once after that. A first write of pass 1's plan would move the page and the scroll on its own, which engines then undo differently, and a function that throws leaves nothing to put back. Taking the paddings out can still leave the page shorter than the scroll, which the browser clamps; the layout after the loop is the one before it, so `refresh()` scrolls back to the position read first. Firefox and WebKit can still fire a `scroll` event, WebKit even where the scroll wasn't clamped. Holding the height with a `min-height` doesn't stop that, and the function would read the page's height with every padding again, so the growth comes back (measured).

`resolveScrollPosition` called inside the function puts the page back for its own read, and such a function keeps pass 1's value, which the dwell correction already makes GSAP's. An evaluation puts back only the paddings still at its own 0, so a `refresh()` of another instance from the function keeps that instance's write. A `ScrollTrigger.refresh()` from the function gets the page back too, from that refresh's first layer handler to its `refresh` event, so GSAP measures what a top-level call would; the function's value still counts. GSAP has taken the scroll by then, cut back if the function's layout is shorter, so that handler also puts the scroll and GSAP's record of it back to where they were before the first evaluation, or GSAP would run every trigger's callbacks at the cut-back scroll. A top-level call would have taken the scroll before any `refreshInit` listener ahead of that handler moved it, so such a move goes back too, and so does a scroll the function itself made before the call. Only those listeners still see the function's layout and the cut-back scroll, and a GSAP refresh that throws before its `refresh` leaves the rest of the function on the page `refresh()` left. Both kinds of suspension also take out the layout of an evaluation the function's runs inside (one whose function called `refresh()` on this instance), and a `resolveScrollPosition` during that GSAP refresh isn't the function's.

### Why a `ResizeObserver`-triggered refresh doesn't loop forever

A common integration pattern (used in `demo/src/main.ts`) watches `document.scrollingElement` with a `ResizeObserver` and calls `refresh()` on change, to catch layout shifts a plain window resize wouldn't. Since `refresh()` itself writes Scene layer dwell padding, which changes the document's own height, this is a feedback loop by construction: writing padding re-triggers the observer.

It settles instead of growing without bound because `refresh()` is idempotent. Once every Scene layer's dwell padding reflects the current (unstickied) layout, recomputing it from that same layout yields the same padding again, so the observer-triggered second `refresh()` changes nothing and no third callback fires. This holds even for a cover layer's `end: 'max'` (verified empirically against `e2e/fixtures/maxEnd.html`, where repeated `refresh()` calls settle immediately), because a cover layer never adds padding itself, so resolving `'max'` after Scene padding has settled doesn't reopen the loop.

## Why `resolveScrollPosition` corrects for lag

Nested sticky introduces visual lag: during a Scene layer's dwell, screen position appears frozen while real scroll keeps advancing. For an element, the lag is the sum of dwell distances from every Scene layer whose freeze starts before that element reaches its position. A freeze that starts later delays nothing the element has already done, even when the element sits inside that layer's trigger.

GSAP string `start`/`end` values (for example `'top 80%'`) do not account for this lag, so plain ScrollTriggers inside the shared container can be off by large distances. `resolveScrollPosition` returns absolute px values with lag correction applied.

Its target element isn't guaranteed to share stuck ancestors with anything else, for the same reason [`createStickyPin`](#how-createstickypin-accounts-for-nested-sticky-lag)'s trigger/endTrigger need the same protection. Once `refresh()` has applied a Scene/Cover wrapper's `position:sticky` CSS, the browser keeps engaging and disengaging it natively as scroll changes, with no further `refresh()` involved. So `resolveScrollPosition` hits an actively-stuck ancestor whenever it runs while scroll sits inside an earlier Scene layer's freeze window, including its documented use as a function-valued `start`/`end` that GSAP re-evaluates during its own refresh. It therefore resets the sticky state of every Scene/Cover wrapper and every pin before measuring `documentTop` and restores it afterwards, the same way `#refreshPins` does, and reads at scroll 0 for what else is stuck around its target, as [Two-pass position measurement](#two-pass-position-measurement) describes. A stuck pin shifts its own box and everything inside it as a stuck wrapper does. For an element outside every container, `getScrollTop` resets the pins of every instance it's given, and reads at scroll 0 the same way.

## Why scroll-margin-top carries the correction

`resolveScrollPosition` fixes the numbers this module hands to GSAP, but it can't help the browser's own scrolling: fragment navigation, `scrollIntoView`, `:target` and friends all run a one-shot calculation from the current layout, and pinning breaks that calculation the same way it breaks GSAP's own `pin`. `scrollMargin.ts`'s own doc comment derives the fix in full (the `landing = currentScroll + paintedTop − scrollMarginTop` formula, and why the correction needs a scroll-dependent term rather than a single constant). A jump started 800px into an 800px freeze window overshot by exactly 800px when the correction used a plain constant instead of the scroll-dependent term.

The rest of this section covers what that comment doesn't: the browser behaviors that shaped the implementation.

### Why each layer's lag decision is a CSS `clamp()`

Whether a Scene layer's dwell delays a target depends on where the target has to stop, and `--sst-scroll-margin-top-offset` moves that point without a `refresh()`. So the decision can't be made in JavaScript at `refresh()` time; it's written into the target's style as `clamp(0px, x * 1000000, dwell)`, which acts as a step. Measured in Chromium, WebKit and Firefox via Playwright, it counts or drops each layer exactly. Firefox's CSS math is less precise: with the positions themselves inside the `calc()`, it counted 2 of 400 exact ties at positions up to 60000px. The module keeps those numbers out of CSS by folding everything but the offset property into one constant in JavaScript, so a value near a tie reaches Firefox small. The step still subtracts 0.05px, the same tolerance `resolveScrollPosition`'s JavaScript comparison uses for its own float error, so both draw the line in one place.

Each layer's `x` is compared against a constant rather than against the lag the earlier layers add up to, which `dwellBeforeReach` shows gives the same answer. Passing that lag from layer to layer through custom properties would reference each one twice, and engines expand `var()` as text, so the value would double per layer. Measured, it reached 300,978 characters at 12 layers, where WebKit discards it as invalid, and all three engines discard it at 16, leaving `scroll-margin-top` at 0.

### Why the animation rule needs an explicit `@supports` gate

Firefox doesn't support `animation-timeline: scroll()`. The natural assumption is that a browser without that support leaves the declaration inert, but it doesn't (verified against real Firefox via Playwright, not inferred from spec text). `animation-timeline: scroll(...)` is unparseable there, so the whole declaration is dropped and `animation-timeline` stays at its initial value `auto`. Under `auto` the `animation` shorthand this module also writes becomes an ordinary time-based animation with no explicit duration, hence 0s. A 0-duration animation with fill-mode `both` still runs, instantly: every custom property jumps straight to its keyframe's `to` value, the layer's full dwell, the moment the page loads. The resulting `scroll-margin-top` lands hundreds of pixels from any real target, worse than doing nothing. Wrapping the animation rule in `@supports (animation-timeline: scroll())` (see `scrollMargin.ts`'s `buildStylesheet`) keeps it from running at all on an engine that can't parse it. The emission is gated as well: an engine that reports no support, or has no constructed stylesheets to carry the rules, drives the ramps from a `scroll` listener and gets no stylesheet at all, which is what `e2e/StickyScrollTrigger.spec.ts`'s Firefox-only test checks. That leaves the `@supports` gate as a second line, for a `CSS.supports()` that disagrees with the parser.

The JS fallback this leaves Firefox with (a `window` `scroll` listener writing the same custom properties) was checked against the Chromium smooth-scroll limitation below and doesn't share it. Every engine that lacks native scroll-timeline support tolerates a `scroll-margin-top` that keeps changing mid-scroll. That limitation is specific to Chromium's compositor, not a general consequence of updating the value dynamically.

### Known limitation: Chromium + native smooth scrolling

Chromium's `scroll-behavior: smooth` doesn't run a fragment jump as one continuous animation: per-frame sampling showed it advancing in several distinct steps, each firing its own `scrollend`, with scroll position occasionally moving backwards briefly between them. A `scroll-margin-top` that changes before the last step makes Chromium recompute the landing target mid-flight and under- or overshoot. Driving the value from CSS or from JS fails identically, and deferring the JS write to each intermediate `scrollend` makes it worse, re-triggering the recomputation on every settle rather than just the first. No variant of a dynamically-changing `scroll-margin-top` avoids this while still landing correctly for a jump started mid-dwell, which is why the demo leaves `scroll-behavior: smooth` off `html`. Sites that need animated same-page scrolling in Chromium should drive it themselves via [`getScrollTop`](README.md#stickyscrolltriggergetscrolltopelement-instances) and `scrollTo({ top, behavior: 'smooth' })` to a precomputed, unchanging target.

### Known limitation: Firefox drops scroll-padding-top after a sticky ancestor engages

Putting a fixed header's offset on `scroll-padding-top` (on the scroller), kept separate from this module's own per-target correction on `scroll-margin-top`, runs into a documented, intentional Firefox heuristic (verified via Playwright): once any `position: sticky` element on the page has ever been stuck, Firefox stops applying `scroll-padding-top` on fragment jumps, assuming the stuck sticky ancestor is itself the header. That assumption doesn't hold for this module's nested-sticky structure, where every Scene layer's sticky wrapper becomes an ancestor of everything after it (see "Nested structure of the Scene and Cover layers" above) whether or not it has anything to do with a header. Any same-page link past a Scene layer silently loses the header offset, landing short by exactly the header height.

The fix is to keep the header offset off `scroll-padding-top` entirely: fold it into `--sst-scroll-margin-top-offset`, so only `scroll-margin-top` is ever in play for a same-page jump. The demo does this in `style.css`'s `html` rule, and `e2e/StickyScrollTrigger.spec.ts`'s `--sst-scroll-margin-top-offset combines correctly with the dwell correction on a jump started mid-dwell` test guards the pattern.

### Why `getScrollTop` is a static method

A target element for a same-page anchor link isn't guaranteed to belong to the particular `StickyScrollTrigger` instance a piece of code happens to have on hand; a page can have more than one, one per shared container. Applying the wrong instance's dwell to a target it never delayed corrupts the result, the same drift `resolveScrollPosition` above exists to correct. So `getScrollTop` takes every candidate instance and checks each one's shared container itself, rather than making the caller know which one owns the target.

Being `static` (called on the class, not an instance) is what makes that check possible at all: private fields are scoped to the class body, not to a particular `this`, so a static method can read `#rootElement` off any instance passed in as an argument, not just its own.

### Why `pin: true` is discouraged alongside this

With default `pinType: 'fixed'`, GSAP extrapolates pin position from scroll state at refresh time (internally: `top: bounds.top + (scroll - start)`). Right after page load (`scroll≈0`), extrapolation toward `start` can be offset by dwell-induced lag between those points. In nested sticky, this can make the element jump when pinning starts, even if `start`/`end` are corrected.

`pinType: 'transform'` avoids the jump but shifts pin tracking to JS updates on scroll, which can visibly lag during fast scrolling. In practice, no `pin: true` setup provides both accurate starts and smooth pinning inside nested sticky.

If you just want to pin part of the shared container without going through GSAP, use `createStickyPin` (in `README.md`). It works purely off `position:sticky`, so it doesn't run into this `pin: true` issue; how it allows for the lag is below.

## Why far-off sticky layers are switched to relative

WebKit lays out nested `position:sticky` about three times slower per level, also with a hand-built nesting and no library involved: with one sticky element per level, 10 levels took 6ms per forced layout and 14 took 450ms (the README's figures are per frame, on a page of Scene layers), while `position: relative` in their place took nothing measurable. A `position: relative` element between levels, `contain: layout` or the same tops without the padding siblings don't help; only fewer sticky levels at once does. So `dormancy.ts` keeps `position:sticky` on an element only while the scroll is near its range and holds it at the same offset with `position: relative` elsewhere.

The ranges come from one page-level table, rebuilt at the end of every `refresh()` of every instance, since an element's range depends on every sticky ancestor above it, whichever instance (or the author) made that one sticky. The build reads the layout once, with the library's sticky elements and every sticky element around them set to `static` (the natural layout, cheap to lay out; an author's sticky element beside them stays out of the table, and one inside them is never written to), and never while they're sticky: that read is the cost being avoided, and taking it would make each refresh as slow as the frames. Each element's range follows from its static top, its sticky top and its travel inside its containing block, pushed later by the merged ranges of its sticky ancestors, which hold it still while they're stuck.

The whole-document scan for sticky elements runs only when the switch can turn on: with every instance on `'auto'`, the depth is read first from the library's own elements and their ancestors alone, which is all a shallow page pays. It also runs once per synchronous run: GSAP's dispatch can call `refresh()` once per layer in one go, and the later builds in it measure the elements already known plus every library-owned one afresh.

The buffer around each range is the viewport height, shrunk in 25px steps while more than four levels along one ancestor chain would be sticky at once, and never below 325px: the largest distance an iPhone moved between two scroll events during hard flings was 306px.

GSAP's own refresh dispatches `refreshInit` (where `refresh()` runs), scrolls to 0 and measures every trigger in the same task, so the table's own `refreshInit` listener, and any build inside the refresh, apply the state for scroll 0. The state for the scroll GSAP returns to goes back from the `render(-1)` GSAP calls on what that listener returned, which runs after every trigger is measured and before `onRefresh`. (When the class is first taken during one of GSAP's refreshes, the listener missed that dispatch, and the instance's own `onRefreshInit` result carries the restore instead.) GSAP's `refresh` event rebuilds the table once more, since GSAP may change its own pin spacing after the instances measured. Telling that refresh apart needs `ScrollTrigger.isRefreshing`, read off the class captured from GSAP's callbacks (gsap is never imported), so without that class the switch stays off rather than show GSAP the wrong layout: a plain ScrollTrigger measured 1100px late that way.

A `refresh()` measures with the switched elements left relative; the build after it takes their own `z-index`/`will-change` from the previous table rather than the values the switch wrote. Switching them back to sticky first would make the refresh's first layout read a full nested-sticky one (GSAP's refresh at 13 levels took 3.9s that way, against 16ms).

## How `createStickyPin` accounts for nested-sticky lag

A pin hands GSAP no scroll positions, but its release still depends on the lag: `trigger` and `endTrigger` can sit on opposite sides of the shared container, and only the one inside lags. `#refreshPinLayers` finds the scroll at which the pin has to let go the way `resolveScrollPosition` does, then sizes `inner` in the container's own coordinates. A pin inside the container stands still with it through every freeze, so the dwell gone by at the release scroll comes off the range. With both elements on the same side, the two corrections cancel out.

Before measuring, `#refreshPins` snapshots and resets every Scene/Cover wrapper's sticky state, the same way pass 1 of [Two-pass position measurement](#two-pass-position-measurement) does for Scene/Cover layers' own positions, so no `documentTop` call is taken while an ancestor is actively stuck.

### Why `trigger` needs to be wrapped

To extend pinning through `endTrigger`, `trigger` needs a containing block that spans that range without pushing later layout down.

`inner` holds the effective pin range, which overflows `outer` without moving anything after it. Every `refresh()` sizes `outer` to `trigger`'s own margin box before anything else is measured (`#reservePinSpace`), so the page keeps the height and the layout it had before the pin was registered. Horizontal sizing is unchanged; `trigger`'s own `width`/`flex` rules still apply.

`#reservePinSpace` measures that margin box instead of computing it: it clears `inner`'s range and `outer`'s own height, then reads back the natural height `outer` collapses to. Because `outer` is a `display: flow-root` formatting context, `trigger`'s margins land inside it rather than collapsing out, so that natural height is the margin box already, resolved by the browser through whatever `box-sizing`, borders, floats or line boxes `trigger` happens to have. Reading it off the computed style (`measureUsedHeight`) keeps the fractional part that `offsetHeight` rounds away, and keeps out a transform that `getBoundingClientRect` would include and no other measurement here does.

Margin collapsing is the one thing the reserved height can't stand in for: `trigger`'s vertical margins stop at `outer` instead of collapsing with its siblings', and no sizing of `outer` can fix that, since the collapsing partner is outside it. A 30px `margin-bottom` above a `trigger` with a 20px `margin-top` occupies 30px unwrapped and 50px wrapped. That leftover shift is why a pin's kill still schedules a deferred `refresh()`. `inner` carries no `overflow` or `contain` of its own on purpose: either would make it a formatting context too, and `trigger`'s top margin would then push it down inside the reserved box rather than collapsing out to `outer`.

`outer` is a flow-root rather than `contain: layout`, which would also confine `inner`'s overflow but makes `outer` a stacking context and the containing block for `trigger`'s fixed-position descendants. Measured in all three engines, a pin's own `z-index` then lost to a later `position: relative` sibling, and a `position: fixed` element inside `trigger` scrolled with the page. Without containment, the one place `inner`'s overflow shows is a range running past the page's end, which made the page taller by that much. `#refreshPinLayers` stops the range at the page's end instead: the page runs out of scroll before such a pin could release anyway. The end is measured with every pin range on the page cleared, whichever instance owns it, since another instance's range, sized for a longer page, would otherwise count as page and keep it from shrinking. A stuck Scene/Cover wrapper carrying the pin further down doesn't count, since all three engines leave sticky offsets out of the scrollable area.

## Lifecycle

Registering a layer or pin records it in `#layers` or `#pinLayers` and builds nothing (a cover's z-order lift aside). `refresh()` builds the nesting from `#layers` and wraps every pin not yet wrapped, and `#builtLayers` keeps the layers the nesting holds (a level a kill left inert drops out), which the next unbuild undoes. Turning the returned vars into a ScrollTrigger, through `ScrollTrigger.create()` or a tween's `scrollTrigger`, also runs `refresh()`: GSAP refreshes a new trigger at once (one whose animation is a timeline, 0.01s later), calling its `onRefreshInit`. Registering and creating one layer at a time therefore rebuilds the nesting at every create; registering everything first builds it once.

An instance is unarmed until its first layer or pin, armed while it has one, and unarmed again once the last one is killed. `destroy()` ends it from either state. `refresh()` does nothing while the instance is unarmed or destroyed.

### Why page-level effects start with the first layer

Arming starts the scroll-margin sync and, where `nestedStickyOptimization` turns it on, adds the instance to the dormancy table. Disarming hands the page back: it takes the instance out of the table, restores the scroll margins and the cover lifts, and unbuilds the nesting. It runs in the kill of the last layer or pin, before the caller's own `onKill`, unless the page is scrolling: then it waits for the scroll to stop (see [Why a kill mid-scroll waits for the scroll to stop](#why-a-kill-mid-scroll-waits-for-the-scroll-to-stop)). The next registration arms the instance again.

This is for `gsap.matchMedia`, which reverts the previous setup and runs the matching one again on every breakpoint switch. A page that creates its instance inside the setup gets a new one per switch, and nothing destroys the old one. Reverting kills the setup's ScrollTriggers with `kill(true)` (ScrollTrigger.js:1256, there for `gsap.context()` and `gsap.matchMedia()`), which runs the library's `onKill` like any other kill, so the old instance has handed the page back before the next setup registers on the same container. If the switch comes mid-scroll, the new setup's first registration runs the old one's waiting disarm before it reads the DOM, also for an old instance on a container around or inside the new one's. When the old instance tore down only after the next setup had built, its unbuild took the new instance's wrappers with its own, and on a page with Scene layers the shared container left the document at the second switch, in all three engines. A `gsap.context()` revert takes the same path.

`destroy()` disarms, unwraps every pin, empties both lists, rejects any later registration and drops the captured ScrollTrigger class. It kills no ScrollTrigger, so GSAP keeps calling the handlers, which then schedule and refresh nothing; the caller's own callbacks still run. A layer or pin whose vars never became a ScrollTrigger never gets an `onKill`, so an instance holding one stays armed until `destroy()`.

### Why kills take effect at different times

A kill takes its layer or pin out of `#layers` or `#pinLayers` at once. What it leaves in the DOM until the next measurement depends on the kind:

- A Scene layer's wrappers stay until the next `refresh()`, which kills in one task share: rebuilding per kill would be O(n²). Rebuilding moves the shared container's subtree, which reloads iframes and drops focus inside it, while a GSAP pin's kill moves nothing else. So when every change since the build is a removal and a Scene layer is left, that `refresh()` leaves each killed level in place, no longer sticky and with a 0px padding, until the next rebuild (a registration, a reorder, or no Scene layer left) or the disarm. A start or end function the pass calls can kill a layer and run `refresh()`, which makes the level inert and writes the other wrappers' tops for the new layout after the outer pass has planned them, so the outer pass then neither writes nor rolls back any Scene wrapper's sticky top.
- A cover layer's wrapper comes off in the kill. It holds `trigger`'s siblings, which the next `gsap.matchMedia` setup reads in the same task (the default `cover` is `trigger.nextElementSibling`). The next `refresh()` handles the rest of the nesting as for a Scene layer.
- A pin is unwrapped in the kill. That restores the margin collapsing its wrappers blocked, which can move everything below (see [Why `trigger` needs to be wrapped](#why-trigger-needs-to-be-wrapped)), so a wrapped pin's kill schedules the same deferred `refresh()`, without rebuilding the nesting.
- The last layer or pin disarms the instance in the kill, unless the page is scrolling, so nothing is left to measure. It keeps the content in place as below once the task is over and before GSAP next measures: in the `refreshInit` of the GSAP refresh that runs the batch, else in a microtask. It doesn't if a registration has armed an instance on that container, or on one around or inside it, since then (one armed all along puts nothing back): a setup run again in the task (a `gsap.context` revert and re-run, say) puts the dwell back, and the content stays put without a scroll, as with GSAP's own pins reverted and created again. Keeping it would shift it by that dwell: 600px for three 200px dwells without anchoring, in all three engines. Nor does it if a scroll has begun by then. GSAP marks a scroll only at the end of its own scroll listener, after its update and `scrollStart` (ScrollTrigger.js:382-388), so a kill from a scroll listener registered before GSAP's, or from `scrollStart`, sees the first scroll after a pause as no scroll yet. Inside GSAP's refresh, before GSAP scrolls back, the record moves at once; a kill from `onRefresh` or the update after it comes once GSAP has scrolled back and cleared the record (ScrollTrigger.js:551-562), so its keep waits for the end of the refresh. Unless GSAP refreshes later in the same task, the deferred step still calls `ScrollTrigger.refresh()` for the triggers left on the page.

Whichever `refresh()` runs first after the kill does the deferred work, including one from a `ScrollTrigger.create()`. The kill only makes sure one runs before GSAP measures again:

- If GSAP refreshes later in the same task (a caller's `ScrollTrigger.refresh()`, or `gsap.matchMedia` after its setups unless the page is mid-scroll; ScrollTrigger.js:2066, 484-487), that `refresh()` runs inside GSAP's `refreshInit` dispatch, before GSAP measures: in whichever comes first of the instance's own `onRefreshInit` handlers and a `refreshInit` listener the kill adds, which covers an instance with no handler left. GSAP records the scroll before that dispatch and scrolls back to it after measuring, so that record is what `refresh()` moves. A resize's refresh leaves it alone, as GSAP does.
- Otherwise a microtask calls `ScrollTrigger.refresh()`, since GSAP reads the function-valued `start`/`end` only when it refreshes, and `refresh()` runs in its `refreshInit` dispatch as above. Run before that call, it would run again in the dispatch: the first handler in a GSAP refresh always refreshes (see [How `refresh()` runs inside GSAP's refresh](#how-refresh-runs-inside-gsaps-refresh)). If no dispatch catches the batch up (no GSAP class, or a listener threw before it did), the microtask runs `refresh()` afterwards, and `refresh()` scrolls itself.
- Either way an error from `refresh()` goes off the stack, so it never stops GSAP's refresh.

The rebuild, or a level made inert, takes the killed layers' dwell off above the viewport, and the content there would jump by it; a kill before the first build took nothing off. So the catch-up first maps the scroll (GSAP's record inside its refresh) back to the unpadded layout under the windows the DOM still holds, and after the rebuild adds the dwell the new windows put before that point. The scroll is read against the layout those windows were measured in: when kills in several instances catch up in one task, an earlier one has already taken dwell off above a later one's container and scrolled, so the later one first takes off how far its outermost container has moved since, once some instance's structure has come down, or lost a level, after its windows were measured (a stuck ancestor moves the container too, but not under its windows: that read is taken at 0, as the windows were). The result is an absolute target: the browser's scroll anchoring may have followed part of the change already (a GSAP pin's spacing goes in its kill, before the record), and a shift added on top would count that twice. Outside GSAP's refresh the scroll moves only when it is half a pixel or more off the target, which on an engine with anchoring is mostly never.

The content at the viewport's top doesn't tell how far the scroll is through a freeze, and the unpadded position alone would put the scroll back at the freeze's start; where an inner trigger sits at its outer's top, the two freezes tie at the same unpadded position, and that position alone wouldn't tell the outer one is already over. So the catch-up records how much of each layer's dwell the scroll has gone through, and each layer that stays keeps that amount, capped at its new length, or its new length in full once the scroll is past it: the layers' scrubs and anything outside the container stay where they were. A layer registered again on its trigger since (a `gsap.context` revert and re-run of one setup while the others stay) keeps the killed one's amount, as a GSAP pin reverted and created again keeps its progress; any other layer registered since counts in full if its freeze starts before the content, as above. A scroll the library makes itself also goes through GSAP's scroll function, which updates the scroll GSAP caches until the scroll event: a trigger created before that scrolls back up to the cached number once it has measured (ScrollTrigger.js:1265, 1565). That function scrolls as well, to the whole pixel, so it runs only when the cache is off, and the library's own scroll goes to a whole pixel too.

### Why a kill mid-scroll waits for the scroll to stop

Keeping the content in place outside GSAP's refresh takes a `scrollTo()`, and on iOS one during momentum stops the fling dead. That covers a layer killing itself in `onLeave` on every engine, since the browser's anchoring doesn't keep content in place mid-scroll. So while GSAP reports a scroll (`ScrollTrigger.isScrolling()`), other than the library's own trip to 0 from rest (see [Two-pass position measurement](#two-pass-position-measurement)), a kill's catch-up waits for it to stop, as GSAP holds its own refresh then (ScrollTrigger.js:484-487):

- The deferred step hands the batch to a poll that checks `isScrolling()` every 100ms, the condition GSAP holds its own refresh on: GSAP keeps reporting a scroll while a pointer is down (ScrollTrigger.js:65-69, 590), and after `ScrollTrigger.disable()` mid-scroll, which stops GSAP's update loop, the held work waits as GSAP's refresh does. A poll rather than GSAP's `scrollEnd`, because `ScrollTrigger.killAll()` removes every GSAP listener and GSAP also fires `scrollEnd` from the first scroll event after a pause.
- The last kill keeps the structure built instead of disarming, and `refresh()` does nothing until it has run. GSAP's undocumented `isUpdating` holds it too: a kill from a trigger callback runs inside GSAP's update, where the first scroll after a pause doesn't read as scrolling yet. An update no scroll started is over by the next microtask, which runs the disarm.
- Once the scroll stops, the held disarm runs first, so the batch's `ScrollTrigger.refresh()` measures without it.
- A GSAP refresh before then still runs the batch from its `refreshInit`, and the held disarm first, since nothing refreshes GSAP again once the scroll stops. A registration on the instance cancels the held disarm and the rebuild reuses the structure without keeping the content, as at rest; a registration by another instance on that container, or on one around or inside it, runs the disarm before it reads the DOM, `createResolvedTrigger()` included (an instance that makes no `create*` call leaves it be), and `destroy()` runs it too and drops the batch. Both keep the content only once the scroll has stopped, and then by the same rule, so a setup that registers in the task leaves the scroll alone. Inside GSAP's update alone (a callback's `destroy()`), whether a scroll has begun shows only once the update is over, so the keep checks `isScrolling()` again then. Mid-scroll they usually come from a revert that a new setup follows, and the scroll that keeps the content would stop a fling; left alone, the content moves as with GSAP's own pins reverted.

Until the scroll stops, the killed layers keep their freeze and their padding, and plain triggers GSAP measures in the meantime see them; `resolveScrollPosition` counts the windows the DOM holds and takes the sticky off their wrappers while it measures, so it does too. A `refresh()` the page calls itself mid-scroll isn't held and keeps the content with a scroll, as does the one a layer or pin created then runs.

### `refresh()` pass order

Each `refresh()` runs these steps in order (`#refreshLayout` holds steps 1 to 9):

1. Build the nesting if none is built yet, or rebuild it if a layer was added or killed or a trigger moved out of DOM order. A change that only removes layers, with a Scene layer left, makes the removed levels inert instead (see [Why kills take effect at different times](#why-kills-take-effect-at-different-times)).
2. Take every cover lift off, so step 3 never mistakes a lift's value for the caller's.
3. Wrap the pins not yet wrapped and size each pin's `outer` to `trigger`'s margin box.
4. Put the cover lifts back over the sibling chain steps 1 and 3 left, even when step 3 throws for a detached `trigger`.
5. Measure the viewport height once, for the Scene/Cover passes and the pins alike.
6. Take every wrapper and pin off sticky, at scroll 0 (see [Two-pass position measurement](#two-pass-position-measurement)), then read what this refresh's padding can't move (phase 1): each Scene and Cover layer, running its start/end functions, and the scroll-margin targets, all inside the container.
7. Plan the Scene and Cover layers as [Two-pass position measurement](#two-pass-position-measurement) describes, calling each Scene layer's function-valued dwell or absolute `end` again in the layout GSAP shows it (see [Why a Scene layer's end function runs twice](#why-a-scene-layers-end-function-runs-twice)), and write the paddings.
8. Read what the padding moves (phase 2): a cover's `endTrigger` outside the container and the document height for a cover's `'max'`, planning the covers again from them, then every pin with its range cleared, running its start/end functions.
9. Write every sticky top and pin range, then sync the scroll margins to the settled freeze windows.
10. Rebuild the page-level dormancy table, also after a throw in steps 1 to 9.
11. Write the scroll-margin ramps from the current scroll, on engines that drive them from script.
12. After a kill, when nothing threw, keep the content at the viewport's top in place: move GSAP's scroll record inside GSAP's refresh, or scroll.
13. Rethrow the error from steps 1 to 9, if there was one.

Every layout read in steps 6 to 8 sees the instance's wrappers and pins unstuck, at scroll 0, and nothing goes sticky again until step 9, after the last of them. Before that write, no more of the wrappers are sticky than the last dormancy table left; after it, every level is, and a read would lay out the whole nesting, the cost the table exists to avoid (see [Why far-off sticky layers are switched to relative](#why-far-off-sticky-layers-are-switched-to-relative)). The `'max'` read leaves every pin range out, since step 9 sizes them only later. Steps 11 and 12 read the scroll, which forces a layout, so they wait for the table; the scroll step 12 starts from is read before step 1. `layoutReads.html` in the e2e suite (Chromium) logs the sticky elements at every layout read in a `refresh()`, a resize and a kill, at rest or held for the end of a scroll, and fails on a read that sees more of them than the table leaves near the scroll. The unit tests under "refresh() pass ordering" hold parts of the order.

Steps 3 and 6 to 9 write their values (pin reserves, paddings, sticky tops, pin ranges) through `commit.ts`, including those cleared to measure past (pin heights, position/top), which step 3 or 9 writes again. A throw before the pins are read puts every wrapper and pin back; a pin's throw keeps the Scene and Cover plan and puts every pin back as the last successful refresh left it. Structure and measurements that undo their own writes (sticky strips, the viewport probe, the pin-range clear) stay in `dom.ts` and `structure.ts`, and dormancy and the scroll margins write their own properties. A lint rule keeps every other module from writing styles, attributes or the element tree.

### How `refresh()` runs inside GSAP's refresh

Every layer's and pin's `onRefreshInit` handler can call `refresh()`. GSAP runs every `refreshInit` listener before it measures anything, so an `onRefreshInit` passed in the vars that changes the layout is measured however late in the dispatch it runs. ([Why far-off sticky layers are switched to relative](#why-far-off-sticky-layers-are-switched-to-relative) covers what the table does in the same dispatch.) The first handler in a GSAP refresh always refreshes. A later one refreshes again only if its layer has an `onRefreshInit` of the caller's, which may have changed anything, or the DOM has changed since the instance's last `refresh()`, which a `MutationObserver` on the document reports. The observer starts after that `refresh()`, ignores the instance's own writes, and stops at GSAP's `refresh` event, or in a microtask if the refresh threw before it. A change another listener makes between two of the instance's handlers through a JavaScript variable or a stylesheet's rules alone shows only in the next refresh, as the README notes. The listener a kill adds refreshes without this check.

GSAP runs the handlers in the order the triggers were created, which with several instances need not be the page's: an instance created after one below it (or unmounted and mounted again) refreshes after it and moves its container, and one whose cover ends at `'max'` or at an `endTrigger` below it refreshes before the instance below moves that. So each instance that refreshed earlier in the same GSAP refresh records what it read outside its own structure (its container's top, the page's height if a cover's `'max'` or a pin read it, and every `endTrigger` outside its root), and a handler that refreshed measures again each one whose reads it moved, once per handler: an instance whose reads such a measurement moves in turn keeps them until the next refresh, so reads that keep moving each other can't multiply the cost. A handler that didn't refresh reads nothing for it. The record lasts until a microtask, so two GSAP refreshes in one task (a resize handler's own and GSAP's, say) share it. A read made while another instance's pin is stuck includes that pin's stuck offset, before and after the other handler alike, so this doesn't change it.

GSAP's dispatch has no `try`/`catch` (`_dispatch` maps over the listeners), so an error escaping a handler would stop every later listener and every trigger's measurement on the page. The handlers catch what `refresh()` throws and rethrow it in a microtask, off GSAP's stack. A throw from the caller's own `onRefreshInit` goes through as it would from a plain ScrollTrigger's.

Every run-time access to GSAP goes through `gsap.ts`: the class read off the callbacks' `self`, `isRefreshing`, `isScrolling()`, `isUpdating`, the scroll function and its record, the `refreshInit` and `refresh` listeners, `ScrollTrigger.refresh()`, and the value a `refreshInit` listener returns for `render(-1)`. Much of it is undocumented, so each access skips what is absent, and a GSAP upgrade is checked in that one file. A lint rule keeps the GSAP-only names (`isRefreshing`, `isScrolling`, `isUpdating`, `getScrollFunc`, `rec`, the two listeners) out of other modules; `refresh()`, `self.constructor` and the returned value look like the library's own code, so review covers them.
